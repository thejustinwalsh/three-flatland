`Flatland` is the high-level entry point for three-flatland. It wraps a `SpriteGroup` with an
orthographic camera, global uniforms, a post-processing pipeline, and render-target support in a
single object.

For setup, the render loop, post-processing, and disposal, see
[Set up a Flatland scene](../flatland-setup/). For every constructor option and method, see the
[`Flatland` API reference](/three-flatland/api/three-flatland/src/classes/flatland/).

## Flatland compared with SpriteGroup

|                     | Flatland                                   | SpriteGroup                       |
| ------------------- | ------------------------------------------ | --------------------------------- |
| **Use case**        | Self-contained 2D pipeline                 | Embed sprites into your own scene |
| **Camera**          | Internal pixel-perfect orthographic camera | You provide the camera            |
| **Post-processing** | Built-in pass effect pipeline              | Not included                      |
| **Global uniforms** | Automatic time, viewport, tint             | Not included                      |
| **Render call**     | `flatland.render(...)`                     | `renderer.render(...)`            |

The difference is which object owns the frame. `Flatland` owns the camera, the sizing, and the
render call, so a 2D scene needs no render loop beyond one `render()` call. `SpriteGroup` owns
none of those, so it fits inside a 3D scene that already has a camera and a render loop of its own.

Use `SpriteGroup` when an existing scene already owns the camera and the render loop. Use
`Flatland` when none does.

## Frame synchronization

<Diagram caption="Per-frame render pipeline" src={framePipeline} />

`render()` synchronizes four things before it draws: the camera, the global uniforms, the
lighting buffers, and the sprite batches. Flatland recomputes all four every frame, so your
application does not maintain them between frames.

Flatland also tracks the render surface. It reads the size of the renderer's drawing buffer, or of
the active render target, and updates the camera when that size changes. You do not need a resize
listener.

Two size units are in use. Surface-dependent GPU resources are measured in physical
drawing-buffer pixels, which puts canvas device pixel ratio and render-target texels in one
coordinate space. [Pixel-perfect rendering](../pixel-perfect-rendering/) covers both units and the
sizing rules in full. `globals.viewportSize` reports the renderer's logical size instead, paired
with `globals.pixelRatio`.

The default camera, `PixelPerfectCamera`, selects an integer scale and centers the resulting
viewport inside the surface. When that viewport does not fill the surface, bars remain along two
edges, and `resolvedAspect` then reports the ratio of the viewport rather than of the whole
surface.

## Object routing

`add()` dispatches on type, so the caller does not choose a destination. `Sprite2D` instances go
to the internal `SpriteGroup` and become batch candidates, and `Light2D` instances register with
the lighting system. Anything else is a plain `Object3D` that joins the internal scene directly.

Flatland connects global uniforms to a sprite's material when `add()` places it. This holds
regardless of when the sprite joins the scene, so every sprite reads the same global uniform
values, including `time`.

## Global time

`globals.time` is `undefined` by default, and Flatland accumulates elapsed seconds automatically.
Assigning it a number overrides that: shaders read the value you set instead, and Flatland stops
advancing it.

## Effect ownership

A `LightEffect` is the lighting pipeline a `Flatland` instance runs each frame. An attached
instance belongs to the `Flatland` that holds it. Replacing the active effect, or clearing it,
disposes the effect's GPU resources before detaching it. Attaching it again produces a fresh
`init → resize → update` sequence. A handle the effect produced while attached must not be used
once the effect is detached.

`dispose()` applies the same contract to the whole object: it destroys the entity-component-system
(ECS) world, the sprite batches, the render pipeline, and every pass effect entity together.

## Post-processing cost

Adding the first pass changes how a frame is drawn. With no passes, the scene draws directly to
the destination. With one or more, the scene renders to an offscreen target, and each pass runs as
a full-screen draw over it.

:::tip[Performance note]
One or two passes are cheap. A long chain costs a full-screen sample per pass per frame, so
combine effects into a single pass where you can.
:::

That switch is invisible from the API. Because the render pipeline initializes on the first
`addPass()` call, that call costs more than each one after it.
