`Flatland` is the high-level entry point for three-flatland. It wraps a `SpriteGroup` with an
orthographic camera, global uniforms, a post-processing pipeline, and render-target support in a
single object.

For setup, the render loop, post-processing, and disposal, see
[Set up a Flatland scene](../flatland-setup/). For every constructor option and method, see the
[`Flatland` API reference](/three-flatland/api/three-flatland/src/classes/flatland/).

## Flatland compared with SpriteGroup

|                     | Flatland                                   | SpriteGroup                       |
| ------------------- | ------------------------------------------ | --------------------------------- |
| **Use case**        | Self-contained 2D pipeline                 | Embed sprites into your own scene |
| **Camera**          | Internal pixel-perfect orthographic camera | You provide the camera            |
| **Post-processing** | Built-in pass effect pipeline              | Not included                      |
| **Global uniforms** | Automatic time, viewport, tint             | Not included                      |
| **Render call**     | `flatland.render(...)`                     | `renderer.render(...)`            |

The difference is which object owns the frame. `Flatland` owns the camera, the sizing, and the draw,
so a 2D scene needs no render loop beyond one `render()` call. `SpriteGroup` owns none of those,
which is what you want when sprites are one layer inside a 3D scene that already has a camera and a
loop.

Use `SpriteGroup` when an existing scene is authoritative. Use `Flatland` when the 2D scene is the
application.

## Frame synchronization

<Diagram caption="Per-frame render pipeline" src={framePipeline} />

`render()` synchronizes four things and then draws: the camera, the global uniforms, the lighting
buffers, and the sprite batches. All four are derived state, so your application does not maintain
them between frames.

Flatland also tracks the render surface. It reads the size of the renderer's drawing buffer, or of
the active render target, and updates the camera when that size changes. You do not need a resize
listener.

Two size units are in use. Surface-dependent GPU resources are measured in physical drawing-buffer
pixels, which puts canvas device pixel ratio and render-target texels in one coordinate space.
[Pixel-perfect rendering](../pixel-perfect-rendering/) covers both, and the sizing rules in full.
`globals.viewportSize` reports the renderer's logical size instead, paired with
`globals.pixelRatio`. Effects allocate against physical pixels; shader layout code uses the logical
size.

The default camera, `PixelPerfectCamera`, selects a whole-number scale and centers the viewport
inside the surface. That scale usually does not fill the surface exactly, so bars remain along two
edges. `resolvedAspect` then reports the ratio of the viewport rather than of the whole surface.

## Object routing

`add()` dispatches on type, so the caller does not choose a destination. `Sprite2D` instances go to
the internal `SpriteGroup` and become batch candidates. `Light2D` instances register with the
lighting system. Anything else is a plain `Object3D` and joins the internal scene directly.

Global uniforms are wired to a sprite's material at `add()` time. A sprite added on frame 200 reads
the same `time` and `globalTint` as one added on frame 1.

## Global time

`globals.time` is `undefined` by default, and Flatland accumulates elapsed seconds itself. Assigning
a number takes that over: the value you set is the value shaders read, and Flatland stops advancing
it. Fixed-step simulations and deterministic replays need that control; most scenes do not.

## Effect ownership

An attached `LightEffect` belongs to the `Flatland` that holds it. Replacing the active effect, or
clearing it, disposes the effect's GPU resources before detaching it. The instance can be attached
again and receives a fresh `init → resize → update` sequence. Handles it produced while attached
become invalid once it is detached.

`dispose()` applies the same contract to the whole object. The ECS world, the sprite batches, the
render pipeline, and every pass effect entity are destroyed together. Ownership is never shared, so
two objects cannot hold conflicting claims on one buffer.

## Post-processing cost

Adding the first pass changes how a frame is drawn. With no passes, the scene draws straight to the
destination. With one or more, the scene renders to an offscreen target and each pass runs as a
full-screen draw over it.

:::tip[Performance note]
One or two passes are cheap. A long chain costs a full-screen sample per pass per frame, so combine
effects into a single pass where the math allows it.
:::

That switch is invisible from the API, and it is why the first `addPass()` call costs more than the
second.
